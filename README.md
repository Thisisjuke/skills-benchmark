# Skillbench

Skillbench helps you find out whether an Agent Skill is actually better—not just
different. It turns skills and evaluation suites into reproducible inputs, then lets
you inspect, evaluate, compare, and merge them from a CLI or a local Web application.

## Why Skillbench exists

Agent Skills are easy to edit and difficult to judge. A rewrite can sound clearer
while performing worse, two authors can solve the same problem in incompatible ways,
and a promising merge can regress on cases that were not used to create it.

Skillbench gives that work a repeatable loop:

1. resolve local or GitHub-hosted skills to fingerprinted snapshots;
2. run both skills against the same versioned evaluation suite;
3. compare results with an explicit runner, model, and judging configuration;
4. generate merge candidates and optionally validate the winner on a holdout suite;
5. keep each interactive run as a portable, human-readable result bundle for review.

You can use the free deterministic mock runner to exercise the workflow, or connect an
installed Codex or Claude executable for meaningful model-backed evaluations. The
Promptfoo assertion engine is included; it does not need to be installed separately.

## What's in this repository?

This Vite+ monorepo produces two public npm packages and keeps their shared internals
behind private workspace boundaries.

| Product or area | What it is | Browse the code |
| --- | --- | --- |
| `@thisisjuke/skillbench` | One-off CLI for inspecting, evaluating, comparing, and merging skills | [`packages/cli/`](packages/cli/) |
| `@thisisjuke/skillbench-web` | Persistent local UI that runs the CLI and stores jobs and results in SQLite | [`apps/web/`](apps/web/) |
| Shared packages | SDK, contracts, runners, GitHub source adapter, and assertion adapter bundled into the products | [`packages/`](packages/) |
| Applications | User-facing applications and their runtime boundaries | [`apps/`](apps/) |
| Repository tooling | Boundary checks, runtime-instruction checks, and release smoke tests | [`scripts/`](scripts/) |
| Ready-made example | Two local skills, development and holdout suites, and a mock-runner configuration | [`packages/cli/examples/basic/`](packages/cli/examples/basic/) |

Only the CLI and Web application are published. The private `@skillbench/*` packages
are architectural boundaries, not packages users install separately.

## Try Skillbench

Requirements: Node.js 22.22.2 or newer. Remote examples also require network access.

### Inspect a remote skill transiently—no project setup

`inspect` does not run a model. Disable prompts for a one-off run that neither
initializes a project nor saves a bundle:

```sh
npx @thisisjuke/skillbench inspect \
  https://github.com/Thisisjuke/skills/tree/main/common/domain-modeling \
  --no-input --no-output
```

### Compare two remote skills in a disposable playground

Create an empty directory so every project file generated by Skillbench has an obvious
home:

```sh
mkdir skillbench-playground
cd skillbench-playground
npx @thisisjuke/skillbench init --no-input
npx @thisisjuke/skillbench compare \
  https://github.com/Thisisjuke/skills/tree/main/common/domain-modeling \
  https://github.com/mattpocock/skills/tree/main/skills/engineering/domain-modeling \
  --repeat 1
```

`init --no-input` selects the free mock runner, so this is a workflow smoke test rather
than a meaningful quality ranking. For real evaluations, run interactive `init` and
choose an installed, authenticated Codex or Claude runner.

The current directory becomes the Skillbench project. Versionable configuration,
evaluation suites, and model-facing instructions live under `.skillbench/`; only
generated subdirectories such as runs, temporary workspaces, caches, and Web state are
ignored. Interactive commands save unique bundles below `.skillbench/runs/` by default.
Use `--no-output` to opt out, or `--output <directory>` to choose an exact destination.
Automation remains explicit and does not create a bundle unless it passes `--output`.

Continue with the [CLI journey](packages/cli/README.md#try-the-remote-skill-journey) to
inspect, compare, and merge the same two remote skills.

### Open the local Web application

From an initialized project:

```sh
npx @thisisjuke/skillbench-web --project .
```

The browser opens automatically. Use `--no-open` to start only the loopback server.
The [`apps/web/` guide](apps/web/README.md) covers storage, lifecycle, and development.

## How the products fit together

```text
skillbench-web → public CLI binary and contracts → CLI composition
                                                   ├→ runner adapters → runner-kit → SDK
                                                   ├→ GitHub source adapter ─────────→ SDK
                                                   └→ Promptfoo assertion adapter ───→ SDK
SDK → invocation-contract              test-contracts → SDK + invocation-contract
```

Dependencies point toward contracts, never toward a product higher in the graph. The
SDK is independent of Commander, React, Drizzle, and concrete providers. The CLI
composes adapters but owns no database. The Web application alone owns SQLite and runs
the exact installed CLI version as a subprocess.

The [`packages/` map](packages/README.md) is the canonical dependency and ownership
guide. Executable guards live in
[`scripts/check-workspace-boundaries.mjs`](scripts/check-workspace-boundaries.mjs) and
[`scripts/check-runtime-instructions.mjs`](scripts/check-runtime-instructions.mjs).

## Develop the monorepo

The repository pins pnpm 11.24.0 and Vite+ 0.3.0. Vite+ is the task orchestrator.

```sh
corepack enable
vp install --frozen-lockfile
vp run skillbench -- --help
vp run check
```

Common commands:

| Goal | Command |
| --- | --- |
| Run a workspace check | `vp -C packages/sdk run check` |
| Start Web development | `vp run dev` |
| Build both public products | `vp run build` |
| Check dependency boundaries | `vp run boundaries` |
| Check runtime instruction ownership | `vp run instructions` |
| Run the complete repository gate | `vp run check` |
| Pack and exercise both products externally | `vp run smoke:release` |

Real Codex, Claude, and GitHub tests are opt-in because they require an authenticated
executable, network access, or tokens. Each adapter README owns its exact live-test
command. Ordinary `test` and `check` tasks exclude those live files.

### Find the right owner before changing code

Start with the [package ownership guide](packages/README.md#choosing-an-owner). A
workspace is justified by an independent contract—not by file size alone. New
workspaces must declare internal dependencies with `workspace:*`, avoid sibling `src`
imports, document their ownership, join the boundary graph, and prove any public
tarball outside the workspace.

## Distribution and releases

Only `@thisisjuke/skillbench` and `@thisisjuke/skillbench-web` are public artifacts.
Private production workspaces are bundled into them. The release smoke builds and packs
each product once, installs both tarballs in temporary external projects, and records
the accepted paths and SHA-512 integrities in `artifacts/release-artifacts.json`.
Publication must consume those artifacts without repacking.

The CLI and Web versions currently move together under one `vX.Y.Z` tag. Changesets
owns versions and changelogs; the tag-driven workflow owns publication.

For every user-visible product change:

```sh
vp run changeset
```

To prepare a release:

```sh
vp run version-packages
vp install
vp run check
```

Commit the two product manifests, both changelogs, consumed changesets, and lockfile.
After confirming the versions match, push one `vX.Y.Z` tag and monitor the `Release`
workflow. It validates the tag, runs the full gate and external-consumer smoke, then
publishes CLI before Web.

### One-time npm trusted-publisher setup

The permanent workflow is tokenless. On npmjs.com, configure both packages with owner
`Thisisjuke`, repository `skills-benchmark`, workflow `release.yml`, and permission to
run `npm publish`. Leave the environment blank unless the workflow is updated to use
the same protected GitHub environment.

If a package must exist first, run `vp run smoke:release`, then bootstrap the two paths
from `artifacts/release-artifacts.json`—CLI first—with a protected granular token and
`--provenance=false`. Revoke the token immediately, configure both trusted publishers,
then prove OIDC and safe reruns with a Changesets prerelease and a
`vX.Y.Z-canary.N` tag. See npm's [trusted publisher
documentation](https://docs.npmjs.com/trusted-publishers/) and the [Changesets usage
guide](https://github.com/changesets/changesets/blob/main/docs/intro-to-using-changesets.md).

## Security

Repositories, skills, fixtures, and `command` assertions are potentially untrusted
content. Workspaces reduce collisions but are not a complete operating-system sandbox.
Use minimum permissions, inspect suites, and execute only sources you trust.

`--debug` output is sanitized, but secrets should never be added deliberately to
prompts, fixtures, or results. Provider packages document their own sandbox and
environment limitations.
